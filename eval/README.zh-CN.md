# PanKB LLM — 检索与生成评估

> English version: [README.md](README.md)(以英文版为准)

PanKB RAG 系统的评估框架。目的是回答已发表工作没有回答的问题:论文只报告了一个**端到端**准确率(88%,最优系统 92%),**完全没有检索层指标**。这意味着答错时无法归因 —— 分不清是检索没找到,还是找到了但模型没用好。

分三层独立评估,才能归因:

| 层 | 问题 | 指标 | 状态 |
|---|---|---|---|
| 检索 | 含答案的段落找到了吗? | recall@k, nDCG@k, MRR | 进行中 |
| 生成 | 给了正确 context,模型会用吗? | accuracy, faithfulness | 计划中 |
| 端到端 | 整条链路效果如何? | accuracy(四分类), faithfulness | 计划中 |

## 评测集

`questions.json` / `questions.csv` —— PanKB 论文(doi:10.1093/nar/gkae1042)补充材料 Table S1 里的 50 题,通过 EuropePMC 补充文件 API 取得。`Table_S1_original.xlsx` 是未经修改的原始文件,保留用于溯源(provenance)。

每题包含三个字段:

- `question` —— 问题
- `source_doi` —— 答案出自哪篇论文。**论文方法部分从未提及这一栏**,但数据里有;正是它让检索评估成为可能
- `reference_answer` —— 从该论文摘录的原文片段

**已知缺陷,明确处理而非默默忽略**:

- **Q26 没有标准答案**(Table S1 里该格为空)。排除,不计入评分。
- **覆盖极不均衡。** 50 题只来自 20 篇论文,且前 3 篇贡献了 22 题(44%)。所以**结果必须按来源论文分层报告**,不能只看总分 —— 否则某个模型只要恰好适合那几篇主导论文,分数就会被抬高。
- **Q01/Q02 指向同一段原文**,题目之间并非完全独立(算统计显著性时要注意)。
- 答案是原文逐字摘录,最长 1704 字符,所以**判分必须用 judge**,字符串比对毫无意义。

**许可**:题目集本身可再分发(PanKB 论文是 CC-BY),但 `reference_answer` 引用了 20 篇第三方论文的原文,其中多数**不是** CC-BY。作为私有评测集使用没问题;如果要公开发布,需要再评估一次。

## 语料

`corpus/papers_subset/` —— 170 篇论文,用于构建实验用向量库:

- **20 篇正样本** —— 50 题的来源论文
- **150 篇噪声** —— 从其余文献库中按固定种子随机抽取,作为干扰项,让检索指标有区分度

来自 `origin/develop:Paper_all/`(共 833 篇),**全部从 git 恢复,不下载任何东西**。噪声抽样使用固定种子,因此重跑脚本会得到**逐字节相同**的语料。

**为什么用子集而不是全量生产库**(106k chunk):比较 embedding 模型意味着每换一个模型就要把整个库重新 embedding 一遍。子集让这件事变得便宜。

⚠️ **代价必须说清楚**:子集的干扰项比生产库少,所以**绝对 recall 会偏高**。但它**不影响模型之间的相对排序** —— 因为所有模型面对的是同一个语料。引用数字时必须标明"这是子集数字"。

## 脚本

从仓库根目录按顺序运行:

```bash
python3 eval/scripts/01_build_subset_corpus.py       # 从 git 重建语料
python3 eval/scripts/02_build_chunk_ground_truth.py  # 把答案定位到 chunk
python3 eval/scripts/03_verify_ground_truth.py       # 验证 ground truth
```

**数据访问范围**:`01` 只读 git;`02` 和 `03` 以**只读**方式访问**生产**向量库(`pankb_llm.pankb_vector_store`),**从不写入**。

### Ground truth 构建(`02`)

Recall 的定义是 `召回的相关文档 / 实际存在的相关文档`。**分母必须独立于任何检索器确定** —— 否则每个模型都在和自己的分母比,数字无法横向比较。因此 `02` 使用**纯文本匹配**:不调用 embedding 模型,不做向量检索。

**一个实测发现,也是这个脚本被重写的原因**:

答案(中位数约 300 字符,最长 1704)比 500 字符的 chunk 更长,所以**答案经常跨越 chunk 边界**。第一版逐个 chunk 与答案比对,在 6/50 题上失败 —— 尽管那些段落明明就在论文里。

最清楚的例子是 Q40:答案开头是 *"Type II methanotrophs, exemplified by Methylosinus..."*,而库里对应 chunk 从 *"exemplified by Methylosinus..."* 才开始 —— **开头几个词落在前一个 chunk 里,100 字符的 overlap 没接住。**

改进后的做法是反过来:

1. 把该论文的所有 chunk 按存储顺序**重组成完整文本**,同时记录每个 chunk 的字符区间
2. 在重组文本中**定位答案段落**(先精确匹配,失败再模糊对齐)
3. 标记**所有与该段落区间重叠的 chunk**

因此 ground truth 天然是**一对多**的 —— 这也是更诚实的表示:检索器只要召回了携带答案任一部分的 chunk,就算做了有用的工作。

**当前结果:47/50 可用** —— 19 精确匹配、28 模糊匹配、2 未匹配、1 无标准答案。每题中位数 2 个相关 chunk(范围 1–5)。

> 💡 这个发现的意义超出修 bug:它**实证了当前 chunking 策略会切断语义单元**。500 字符 + 100 overlap 对这个语料是不够的。

#### 为什么「一对多」对指标至关重要

多 chunk 结构不是需要被工程手段消除的麻烦 —— **它正是 recall 在这里有意义的前提。**

如果每题只有 1 个相关 chunk,recall 只能取 0 或 1,**退化成准确率**:两个模型都"找到了 30 题"就无法区分,哪怕一个召回的是核心段落、另一个只蹭到边缘。

有了多个相关 chunk,recall 变成连续值(3 个相关 chunk 的题可以得 0.33 / 0.67 / 1.00),**区分度由此而来**。nDCG 同理 —— 只有一个相关文档时,它基本退化成 MRR。

本实验采用**严格 recall**:`召回的相关chunk数 / 相关chunk总数`,而不是"召回任一相关 chunk 即记 1"的命中率(hit rate)。命中率回答的是另一个运营层面的问题("这题到底能不能被回答"),值得日后补充,但它是二值的,**用来比较 embedding 模型太钝**。

#### 关于 chunk size 与 overlap

**不存在能让答案停止跨界的 chunk size。** 最长的标准答案有 1704 字符;大到能装下它的 chunk,会稀释所有短段落的向量 —— 一个 chunk 混进多个主题,检索精度反而崩坏。

| | chunk 太小 | chunk 太大 |
|---|---|---|
| 检索精度 | ✅ 高(定位准) | ❌ 低(向量被稀释) |
| 语义完整 | ❌ 差(切断答案) | ✅ 好 |
| context 效率 | ✅ 省 token | ❌ 塞入大量无关内容 |

所以**跨界是常态**,一对多的 ground truth 是对这个事实的诚实建模,而非试图消灭它。

**加大 `chunk_overlap` 也不是免费的**:它能减少语义切断,但会让向量库膨胀,并制造大量近似重复的 chunk —— 极端情况下 top-k 里全是同一段文字的不同切法,**recall 数字虚高,而 context 携带的独立信息反而更少**。

这些参数可调,本框架也有能力测量它们,但**每改一次都要把整个语料重新 embedding**。因此暂不处理:本次实验将 chunking 固定在生产配置(500 / 100),**确保 embedding 模型是唯一变量**。

### 验证(`03`)

**未经验证的 ground truth 是检索评估中最危险的失败模式** —— 所有下游数字看起来都很严谨,但地基是歪的。`03` 用三种方式检查:

1. **自动化合理性检查** —— 逼近阈值的模糊匹配、过短的相关 chunk(标题碎片)、无法解析的 chunk id
2. **Token 重叠确认** —— **独立于**构建时用的对齐算法。看答案中的实词有多大比例真的出现在被标记的 chunk 里。这能抓出"位置对齐分数不错但落在错误段落"的情况
3. **人工抽检文件**(`results/ground_truth_review.txt`)—— 把每题的答案和它的 chunk 原文并排列出供人眼核对。**自动化检查无法证明分母正确,最终仍需人看。**

**当前结果**:token 重叠中位数 **1.00**、最低 **0.73**、无一低于 0.55 警戒线、chunk id 全部可解析。最弱的两条对齐(Q44 0.73、Q42 0.78)**已人工核对,均正确** —— 分数低于 1.0 仅仅是因为答案跨越了 chunk 边界。

## 结果产物

`results/` 存放生成的产物(ground truth、验证报告、检索运行结果)。

**这些文件是有意提交进版本库的**:一个指标只有连同它所依据的**确切题目集、语料、ground truth** 一起,才有意义。

## 向量库相关注意事项

- **Azure Cosmos DB for MongoDB vCore 最大支持 2000 维。** 这个约束对模型选型的限制比质量因素更大。
- ⚠️ **生产 HNSW 索引建在 `similarity: "L2"` 上,不是 cosine。** 两者**仅对归一化向量**排序等价 —— 这个前提对当前模型成立,但**代码里任何地方都没写**。

  因此:**任何候选 embedding 模型在采信其数字之前,必须先实测输出向量的模长**;经过维度截断的向量尤其要查(截断会改变模长)。
